# Simulation command boundaries

Product actions immediately publish pilot intent and MCP selections. Each physics commit separately records the applied pilot, autoflight, route and environment revisions, fixed-step index, dispatch duration and first application latency. A revision identifies accepted state, not a flight recorder or a queue of every lever movement. Unchanged revisions retain their first application latency; the number does not grow with time since the last command.

Worker stepping captures commands at chunks of at most 16 fixed steps (60 Hz). A pilot change accepted during a chunk is sampled by the next chunk; up to 16 simulated steps can precede sampling, and its first observation follows at most another 16 steps. Held trim remains immediate pilot intent while the observation retains the trim actually simulated. AP, executed route, environment and aircraft replacement changes fence the old generation. A staged route is inert until EXEC. Pause/reset reject old successes and errors. New frames bank wall time while awaiting a worker; old results cannot replace that bank or its latest timestamp.

One rendered frame reserves at most 128 steps at accelerated rates, or 16 at 1x. Excess time is explicitly recorded as dropped simulation time. The existing worker transport watchdog is 500 ms per request, with one validated main-thread fallback and late-response rejection. Thus two transport turns bound the waiting portion of an ordinary pilot command to 1,000 ms while the event loop is serviced; render scheduling, main-thread stepping and an unresponsive browser add time. This is not an unconditional real-time guarantee. Telemetry exposes measured first application latency and batch duration. The requested rate is separate from achieved simulated seconds per active wall second, measured over one-second windows; pause resets that window.

No rendering interpolation feeds physics, FMA, navigation or stored state. A structural command can restore the outstanding reserved time for new work, but it cannot publish an old result. Numerical faults remain contained and cannot be retried through fallback to conceal invalid output.

## Evidence and remaining acceptance

Unit regressions inject AP disconnect, EXEC, throttle, held trim, pause/rate windows, banked frames and high-rate catch-up. Equivalent explicit command schedules compare the synchronous and worker-handler lanes; that comparison is not a browser-worker receipt.

`e2e/rfs-runtime-latency.spec.ts` separately uses actual Chromium workers with fallback forbidden. It measures cold and warm batch cost and inserts a controlled delivery barrier around actual worker results for AP disconnect, EXEC, throttle, pause and reset. Those results establish protocol/store integration under the injected schedules. They are not blackbox flight completion or representative physical desktop/mobile performance acceptance. Local Chromium measurements supported the 16-step boundary, with 128-step frame work bounded for the synchronous path; device qualification remains in #90. The test records individual measurements rather than claiming a universal percentile from five samples.

Coherent instrument observations and their age are tracked in #147. App/worker release cohorts and installed-PWA update acceptance are tracked in #118. These boundaries continue to use the same immutable committed observation rather than interpolated camera poses.
